# ЕГЭ №26. Обработка и оптимизация данных

## Что проверяет задание

Задание №26 проверяет умение читать большой файл с данными, моделировать описанный в условии процесс и получать требуемые характеристики.

В проекте демоверсии ЕГЭ-2027 рассматривается журнал работы сервера. Для каждого запроса известны:

- время регистрации;
- идентификатор клиента;
- объём переданных данных.

Сервер сохраняет данные в разделе памяти объёма `K`. Если очередной запрос уже не помещается, сервер:

1. создаёт резервную копию всех накопленных данных;
2. очищает раздел памяти;
3. после этого сохраняет данные нового запроса.

Нужно определить:

1. ID клиента, передавшего наибольший суммарный объём данных;
2. сумму объёмов двух наибольших резервных копий, созданных не позднее `11:59:59`.

Для файла демоверсии ответ:

```text
7040 52204
```

---

# Главная идея

№26 почти никогда не решается одной «волшебной» функцией.

Обычно задача состоит из нескольких независимых частей:

```text
прочитать данные
→ понять, что нужно накапливать
→ правильно смоделировать процесс
→ хранить только действительно нужную информацию
→ вывести результат
```

Для демоверсии одновременно нужны два механизма:

```text
1. словарь: общий объём данных каждого клиента
2. переменная текущего заполнения памяти + два максимума резервных копий
```

---

# Формат входного файла

Первая строка:

```text
N K
```

где:

- `N` — количество запросов;
- `K` — вместимость памяти.

Далее идут строки вида:

```text
ЧЧ:ММ:СС C S
```

где:

- `C` — ID клиента;
- `S` — объём данных.

Пример:

```text
8 140000
01:01:01 101 20000
03:03:03 202 110000
05:05:05 101 90000
```

---

# Часть 1. Суммарный объём каждого клиента

Для этого удобно использовать словарь.

```python
clients = {}

clients[c] = clients.get(c, 0) + s
```

Если клиент встретился впервые:

```python
clients.get(c, 0)
```

вернёт `0`.

Если уже встречался — вернётся накопленная сумма.

После обработки всех запросов:

```python
best_client = max(clients, key=clients.get)
```

`max()` перебирает ключи словаря, а

```python
key=clients.get
```

заставляет сравнивать их по соответствующим суммам.

---

# Часть 2. Моделирование памяти сервера

Пусть:

```python
used = 0
```

— объём данных, уже находящихся в памяти.

Для нового запроса объёма `s` проверяем:

```python
if used + s > K:
```

Если условие истинно, новый запрос уже не помещается.

Значит, **сначала** создаётся резервная копия объёма `used`, память очищается, и только затем новый запрос становится первым элементом нового блока:

```python
used = s
```

Если места достаточно:

```python
used += s
```

Это принципиально важно.

Неправильно:

```python
used += s
if used > K:
    ...
```

Потому что тогда в резервную копию фактически попадёт запрос, который в старую память уже не помещался.

---

# Когда создаётся резервная копия

Резервная копия появляется в момент обработки **того запроса, который уже не помещается**.

Поэтому ограничение

```text
не позднее 11:59:59
```

нужно проверять именно для времени текущего запроса, вызвавшего очистку памяти.

Так как время записано строго в формате `ЧЧ:ММ:СС`, строки можно сравнивать напрямую:

```python
if time <= '11:59:59':
```

Например:

```text
'09:45:10' < '11:59:59'
```

работает корректно, потому что часы, минуты и секунды записаны двумя цифрами.

---

# Два наибольших значения без списка

Можно сохранять все размеры резервных копий в список, а затем сортировать.

Но здесь нам нужны только **два максимума**.

Поэтому достаточно:

```python
max1 = 0
max2 = 0
```

При появлении новой резервной копии `x`:

```python
if x > max1:
    max2 = max1
    max1 = x
elif x > max2:
    max2 = x
```

Этот вариант корректно обрабатывает и два одинаковых максимальных значения.

Например, если уже было:

```text
max1 = 100
max2 = 80
```

и появляется ещё одна копия `100`, то она попадёт в `max2`.

---

# Основное решение демоверсии

Если журнал расположен в хронологическом порядке, файл можно обрабатывать **за один проход**.

```python
with open('26.txt') as f:
    n, K = map(int, f.readline().split())

    clients = {}

    used = 0
    max1 = 0
    max2 = 0

    for _ in range(n):
        time, c, s = f.readline().split()
        c = int(c)
        s = int(s)

        # Общий объём данных клиента
        clients[c] = clients.get(c, 0) + s

        # Новый запрос не помещается
        if used + s > K:
            if time <= '11:59:59':
                if used > max1:
                    max2 = max1
                    max1 = used
                elif used > max2:
                    max2 = used

            # память очищена, затем записывается новый запрос
            used = s
        else:
            used += s

best_client = max(clients, key=clients.get)

print(best_client, max1 + max2)
```

---

# Почему последний заполненный блок не считается резервной копией

После чтения файла в памяти может остаться некоторое количество данных:

```python
used > 0
```

Но это **не означает**, что резервная копия была создана.

По условию копия создаётся только тогда, когда очередному запросу не хватает свободной памяти.

Поэтому после цикла нельзя автоматически делать:

```python
backup.append(used)
```

если этого прямо не требует условие задачи.

---

# Если строки файла идут не по времени

Моделирование работы сервера зависит от порядка запросов.

Поэтому перед потоковой обработкой нужно понимать, гарантирует ли условие хронологический порядок записей.

Если такого порядка нет, сначала данные нужно отсортировать по времени.

```python
data = []

with open('26.txt') as f:
    n, K = map(int, f.readline().split())

    for _ in range(n):
        time, c, s = f.readline().split()
        data.append((time, int(c), int(s)))


data.sort()
```

После этого элементы можно обрабатывать в нужной последовательности.

Но при `N` около миллиона хранить весь файл в памяти заметно дороже, поэтому если файл уже упорядочен, однопроходное решение лучше.

---

# Почему №26 нельзя свести только к сортировке

В старых и тренировочных вариантах №26 часто встречаются задачи, где сортировка действительно является главным инструментом:

- выбрать максимальное количество объектов при ограничении;
- распределить товары или места;
- обработать расписание;
- найти соседние свободные места;
- выбрать элементы с минимальной или максимальной суммой;
- смоделировать очередь или хранилище.

Но в демоверсии-2027 важнее именно **моделирование процесса**.

Поэтому перед написанием кода полезно спросить:

```text
Нужно просто выбрать элементы?
→ возможно, сортировка / жадный алгоритм

Нужно воспроизводить события в определённом порядке?
→ моделирование процесса

Нужно накапливать статистику по ID?
→ словарь

Нужны только несколько лучших значений?
→ не обязательно хранить весь список
```

---

# Типовой шаблон: накопление по ключу

```python
d = {}

for key, value in data:
    d[key] = d.get(key, 0) + value
```

Используется, когда нужно найти:

- сумму по каждому клиенту;
- количество событий каждого типа;
- общий объём по идентификатору;
- статистику по участнику, товару, серверу и т. п.

---

# Типовой шаблон: жадный выбор после сортировки

Если нужно взять как можно больше объектов при ограниченной сумме:

```python
a.sort()

s = 0
count = 0

for x in a:
    if s + x <= limit:
        s += x
        count += 1
    else:
        break
```

Идея:

> если нужно максимизировать количество, обычно выгодно сначала брать самые дешёвые / короткие / маленькие объекты.

Но это работает только тогда, когда такая жадная стратегия действительно соответствует условию.

---

# Типовой шаблон: события во времени

Если данные описывают события с моментами начала и конца, часто удобно привести их к единой шкале времени.

Например:

```python
def seconds(t):
    h, m, s = map(int, t.split(':'))
    return h * 3600 + m * 60 + s
```

После этого время становится обычным целым числом.

Это полезно, когда нужно:

- вычислять разницу между моментами;
- сортировать события;
- искать пересечения интервалов;
- моделировать очередь.

Для простой проверки `<= '11:59:59'` в демоверсии преобразование не требуется.

---

# Частые ошибки

1. Добавлять новый запрос в `used` **до** проверки вместимости.
2. После очистки делать `used = 0`, но забывать затем сохранить текущий запрос.
3. Считать остаток памяти после последнего запроса отдельной резервной копией.
4. Искать максимальный отдельный запрос клиента вместо **суммарного** объёма клиента.
5. Сохранять миллион значений в список, хотя достаточно словаря или нескольких переменных.
6. Использовать сортировку автоматически, не проверив, нужна ли она вообще.
7. Игнорировать порядок событий в задачах, где результат зависит от времени.
8. Путать условие `>` и `>=`: если `used + s == K`, запрос помещается полностью, резервная копия ещё не нужна.

---

# Как понять, какой алгоритм выбрать

```text
сумма / количество по ID
→ словарь

события идут последовательно
→ моделирование одним проходом

максимальное количество при ограничении
→ часто сортировка + жадный алгоритм

нужны 2–3 лучших значения
→ хранить несколько максимумов, а не весь список

нужна хронология
→ проверить порядок входного файла

нужна разница между временем
→ перевести время в секунды
```

# Быстрая памятка

```python
# сумма по идентификатору
d[key] = d.get(key, 0) + value

# клиент с максимальной суммой
best = max(d, key=d.get)

# проверка вместимости
if used + x > K:
    # сохранить характеристику старого блока
    used = x
else:
    used += x

# два максимума
if x > max1:
    max2 = max1
    max1 = x
elif x > max2:
    max2 = x
```

Главная мысль №26:

> **Сначала нужно точно смоделировать происходящий процесс, а уже потом выбирать структуры данных и оптимизацию. В хорошем решении хранятся только те данные, которые действительно нужны для ответа.**
